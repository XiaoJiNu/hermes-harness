# A Philosophy of Software Design总结

### 第 1 章 介绍

本章阐述了软件开发的核心挑战是管理复杂性。随着系统功能的增加，其复杂性会累积，使得理解和修改变得困难，从而减慢开发速度并引入缺陷。

作者提出了两种应对复杂性的通用方法：

1. **消除复杂性**：通过使代码更简单、更易懂来直接降低复杂性。
2. **封装复杂性（模块化设计）**：将系统划分为相对独立的模块（如类），每个模块都隐藏其内部的复杂性，开发者可以在不了解其他模块细节的情况下进行工作。

本章还对比了传统的**瀑布式开发模型**和现代的**增量式开发（如敏捷开发）**。瀑布模型试图在项目初期就完成所有设计，但这对于复杂的软件系统来说往往行不通，因为在实现之前无法预见所有问题。增量式开发则更适合软件，因为它允许设计随着经验的积累而持续演进和重构。因此，软件设计是一个贯穿整个生命周期的持续过程，开发者应始终思考如何通过降低复杂性来改进设计。

### 第 2 章 复杂性的本质

本章深入探讨了复杂性的定义、症状和原因。

- **2.1 复杂性的定义**
  - 复杂性被定义为“与软件系统相关的，并且让系统难以理解和修改的任何事物”。一个简单的系统容易理解和修改，而一个复杂的系统则相反。系统的总体复杂性 C 可以粗略地用公式 C=∑pcptp 来描述，其中 cp 是某个部分的复杂性，而 tp 是开发者在该部分花费的时间。
- **2.2 复杂性的症状**
  - **变更放大 (Change Amplification)**：一个看似简单的变更，却需要在很多不同地方修改代码。
  - **认知负荷 (Cognitive Load)**：开发者为了完成一个任务需要了解的大量信息。作者强调，代码行数少不代表认知负荷低；有时需要更多代码行的方法反而更简单。
  - **未知的未知 (Unknown Unknowns)**：必须修改哪些代码或必须获取哪些信息才能完成任务，这些都是不明显的。这是最糟糕的症状，因为它可能导致开发者在不知情的情况下引入缺陷。
- **2.3 复杂性的原因**
  - **依赖性 (Dependencies)**：当一段代码无法被孤立地理解和修改时，就存在依赖。软件设计的目标是减少依赖的数量，并使其尽可能简单和明显。
  - **模糊性 (Obscurity)**：当重要的信息不明显时，就会产生模糊性，例如命名不佳的变量或不清晰的文档。这常常导致“未知的未知”。
- **2.4 复杂性是增量产生的**
  - 复杂性不是由单一的灾难性错误引起的，而是由成千上万个微小问题（小的依赖和模糊之处）随时间累积而成的。

### 第 3 章 能工作的代码是不够的（战略式编程与战术式编程）

本章对比了两种编程心态，并强调了战略式方法的重要性。

- **3.1 战术式编程**
  - 战术式编程的主要目标是让功能尽快工作起来。这种短视的方法会为了短期速度而牺牲设计质量，导致复杂性快速累积。典型的例子是“战术龙卷风”，一位产出代码极快但留下一片混乱的程序员。
- **3.2 战略式编程**
  - 战略式编程的核心理念是“能工作的代码是不够的”，最重要的目标是产生出色的设计。这需要一种投资心态，愿意花费额外的时间来改进系统设计，从而在长远上获得更快的开发速度。
- **3.3 该投资多少？**
  - 作者建议将总开发时间的 10-20% 用于设计改进和重构。虽然这会在短期内减慢速度，但几个月后，开发速度就会超过战术式方法，因为一个更简洁的设计使得添加新功能更容易。
- **3.4 初创公司与投资**
  - 初创公司往往面临巨大压力而采取战术式方法，认为成功后可以再来清理“技术债”。然而，糟糕的代码库会增加未来成本，并使招聘优秀工程师变得困难。作者以 Facebook 的“快速行动，不怕犯错”为例，说明其战术文化导致了代码库问题，后来公司也不得不转向更注重基础架构的战略式方法。

### 第 4 章 模块应该是深的

本章介绍了模块化设计的核心思想，并提出了“深模块”的概念。

- **4.1 模块化设计**
  - 在模块化设计中，系统被分解为多个模块，每个模块都有接口和实现。接口描述模块“做什么”，而实现则包含“如何做”的代码。目标是最大化模块间的独立性。
- **4.3 抽象**
  - 抽象是实体的简化视图，省略了不重要的细节。模块的接口就是一种抽象。一个好的抽象会隐藏所有不重要的细节，但必须暴露所有重要的细节。
- **4.4 深模块**
  - 最好的模块是“深的”：它们通过一个简单的接口提供了强大的功能。模块的价值（功能）远大于其成本（接口的复杂性）。Unix 的文件 I/O 系统和垃圾回收器是深模块的典范，它们用极简的接口隐藏了巨大的实现复杂性。
- **4.5 浅模块**
  - 浅模块的接口与其提供的功能相比，显得过于复杂。例如，一个链表类就很浅，因为其接口的复杂度和其实现的复杂度差不多。浅模块对降低整体系统复杂性贡献甚微。
- **4.6 多类症**
  - 这是一种认为“类越多越好”的错误观念，它导致系统充满了大量微小而浅显的类。每个类本身很简单，但它们接口的累积会使整个系统变得非常复杂。
- **4.7 示例：Java 和 Unix I/O**
  - 作者批评了 Java I/O 库的设计。例如，为了读取一个对象，需要创建 `FileInputStream`, `BufferedInputStream`, 和 `ObjectInputStream` 三个对象。这是一种浅模块的设计，它将缓冲等通用功能从核心功能中分离出来，增加了开发者的认知负荷。相比之下，Unix I/O 的设计使得常见用例（如顺序读写）非常简单。

### 第 5 章 信息隐藏和信息泄露

本章讨论了创建深模块的关键技术：信息隐藏。

- **5.1 信息隐藏**
  - 每个模块都应封装一些代表设计决策的知识，这些知识在其实现内部，但不能通过其接口暴露出来。这能简化模块接口，并使系统更容易演进，因为与隐藏信息相关的变更只会影响单个模块。
- **5.2 信息泄露**
  - 当一个设计决策反映在多个模块中时，就会发生信息泄露。这在模块之间创建了依赖，是软件设计中最重要的危险信号之一。
- **5.3 时间顺序分解**
  - 这是一种常见的设计错误，即代码的结构反映了操作发生的时间顺序。例如，将一个读取、修改、写入文件的应用分为三个类。这往往会导致信息泄露（例如，读和写的类都需要知道文件格式），因为大多数设计决策会在不同时间点显现。设计模块时应关注“知识”，而不是“顺序”。

本章通过一个 **HTTP 服务器** 的例子来说明这些原则。例如，将请求的读取和解析分为两个类就是一种时间顺序分解，会导致信息泄露，因为两个类都需要了解 HTTP 请求的格式。一个更好的设计是将它们合并为一个类，将所有关于请求格式的知识都隐藏起来。另一个例子是参数处理，一个好的设计应该向调用者隐藏参数是在 URL 的第一行还是在请求体中，并自动处理 URL 编码。提供 `getParameter(name)` 这样的方法比返回整个参数映射（Map）要好，因为它隐藏了内部数据结构，是更深的设计。

### 第 6 章 通用的模块是更深的

本章论证了通用化的设计通常比专用化的设计更简单、更深、也更好。

- **6.1 使类的接口足够通用**
  - 作者认为，新模块的最佳实现方式是“有点通用”：即功能反映当前需求，但接口应足够通用以支持多种用途。通用接口通常比专用接口更简单，代码量更少，并且能更好地隐藏信息。
- **6.2/6.3 示例：为编辑器存储文本 / 更通用的 API**
  - 一个文本编辑器项目，如果其文本管理类提供专用的 API 如 `backspace()` 和 `deleteSelection()`，这会将用户界面的概念泄露到底层类中，导致接口臃肿且耦合紧密。
  - 一个更通用的 API，如 `insert(position, text)` 和 `delete(start, end)`，会更优越。虽然上层代码（如实现退格键）会多一两行，但它使得文本类变得通用，更好地隐藏了信息，并减少了认知负荷。
- **6.6 将专用代码上移（或下移！）**
  - 系统中的专用代码不可避免，但应与通用代码清晰地分离。一种方法是**上移**，将专用逻辑（如退格键的行为）保留在更高层级的用户界面代码中。另一种方法是**下移**，例如操作系统的设备驱动程序，它将特定设备的专用代码封装在驱动中，向上提供一个通用的块读写接口。
- **6.7 示例：编辑器撤销机制**
  - 一个好的撤销机制设计，应将通用的核心功能（如管理操作历史列表）与专用的操作（如撤销文本插入或区域选择）分离开。通用部分可以是一个 `History` 类，而专用部分则由不同的 `Action` 子类实现，这些子类可以由系统的不同模块（如文本模块或UI模块）来创建。

### 第 7 章 不同的层级，不同的抽象

本章指出，一个设计良好的系统中，相邻的层级应该提供不同的抽象。如果相邻层级的抽象相似，这是一个危险信号。

- **7.1 透传方法**
  - 当一个方法除了调用另一个签名几乎相同的方法外什么都不做时，这就是一个透传方法。这通常表明类之间的职责划分不清，增加了接口的复杂性而没有提供新功能。解决方法是重新分配职责或合并类。
- **7.3 装饰器**
  - 装饰器模式（Wrapper）通过包装一个现有对象来扩展其功能，但它常常导致产生大量的浅模块和透传方法。作者以 Java I/O 的 `BufferedInputStream` 为例，认为缓冲是一个非常普遍的需求，应该直接整合到基础类中，而不是通过装饰器来添加。
- **7.4 接口与实现**
  - 类的接口所提供的抽象应该与其内部的实现方式有所不同。例如，一个文本类内部可以用行来存储文本，但对外最好提供一个面向字符范围的接口，这样可以封装行拆分和连接的复杂性，使类更深。
- **7.5 透传变量**
  - 当一个变量被作为参数在一长串方法调用中向下传递时，它就是透传变量。这增加了所有中间方法的认知负荷。一个常见的解决方案是引入一个**上下文（Context）对象**，它存储了应用所有的全局状态，并在需要时传递给对象，从而避免了在每个方法调用中都传递这些变量。

### 第 8 章 下沉复杂性

本章提出了一个核心原则：模块的开发者应该承担更多的工作，以便为模块的使用者提供一个更简单的接口。

这个思想被称为**下沉复杂性**，即把复杂性在模块内部处理掉，而不是将其暴露给调用者。例如，一个类不应该因为不确定如何处理某个情况就抛出一个异常，让调用者去处理；它应该自己想办法解决。让模块的接口简单比让其实现简单更重要。

- **示例：编辑器文本类**
  - 一个提供面向行接口的文本类实现起来很简单，但会把行拆分和合并的复杂性推给上层的用户界面代码。而一个提供面向字符范围接口的文本类，虽然自身实现更复杂，但它下沉了这种复杂性，从而简化了整个系统。
- **示例：配置参数**
  - 暴露配置参数常常是一种“偷懒的机会”，它将决定最佳策略的困难问题推给了用户或系统管理员。一个更好的设计是让模块自己动态地计算出合适的值（例如，网络重试间隔），从而下沉复杂性。

### 第 9 章 在一起更好还是分开更好？

本章探讨了何时应该将功能组合在一起，何时应该将它们分开。

细分系统有利有弊。弊端在于它会增加组件数量、管理开销，并可能导致组件间的分离使依赖关系更难被发现。

**应该组合在一起的信号**：

- **共享信息**：如果几段代码都依赖于相同的知识（如文件格式），最好将它们组合在一起以实现信息隐藏。
- **简化接口**：组合模块可以创造一个比原始模块更简单的新接口。
- **消除重复**：将重复的代码提取到一个单独的方法或模块中。

**应该分开的信号**：

- **分离通用和专用代码**：通用机制不应包含针对特定用途的专用代码。专用代码应放在使用它的上层模块中。

本章还讨论了方法的拆分与合并。方法的长度本身不是拆分的好理由；只有当拆分能产生更清晰、更深的抽象时才应该这样做。拆分可能导致浅显的“连体方法”，即必须同时阅读多个方法才能理解它们，这反而增加了复杂性。深度比长度更重要。

### 第 10 章 通过定义来规避错误

本章指出异常处理是复杂性的一个主要来源，并提出了减少异常处理代码的四种技术。

- **10.1 为什么异常会增加复杂性**
  - 异常处理代码中断了正常的控制流，天生比正常代码更难编写和测试。程序员倾向于定义过多的异常，使问题恶化。
- **10.3 通过定义来规避错误**
  - 这是消除异常的最佳方法：重新定义操作的语义，使得原本的错误情况变成正常行为。例如，Tcl 的 `unset` 命令在删除一个不存在的变量时不应该报错，而应该什么都不做，因为它的目标是“确保变量不存在”，这个目标已经达成了。同样，Java 的 `substring` 方法在索引越界时不应抛出异常，而应返回有效的子串部分或空字符串。
- **10.6 屏蔽异常**
  - 在系统的较低级别检测和处理异常，使其对上层软件不可见。例如，TCP 协议通过重传数据包来屏蔽网络丢包的异常。
- **10.7 异常聚合**
  - 用一个通用的异常处理器来处理多种不同类型的异常。例如，一个 Web 服务器可以用一个顶层的处理器来捕获所有服务方法中可能出现的“参数缺失”、“类型错误”等异常，并生成统一的错误响应。
- **10.8 让程序崩溃？**
  - 对于那些极少发生且难以恢复的错误（如内存耗尽），最简单的处理方式就是打印诊断信息然后中止程序。试图处理这类错误会引入大量复杂性，但收效甚微。

### 第 11 章 设计两次

本章提出了一个简单但强大的原则：对于每个主要的设计决策，都应该探索多个选项，而不是满足于第一个想到的想法。

当你面临一个设计问题时（如设计一个类的接口），应该构思几种差异较大的备选方案。然后，列出每个方案的优缺点进行比较。这个过程会加深你对问题的理解，最终可能选择其中一个方案，或者将它们的优点结合起来形成一个更好的新设计。

作者强调，即使是再聪明的人，其第一个想法也不太可能是最好的。花少量额外时间（例如一两个小时）来探索备选方案，其回报（一个明显更好的设计）将远远超过投入的时间。这个过程不仅能改善当前的设计，还能提升你的设计能力。

### 第 12 章 不写注释的四个借口

本章驳斥了开发者不写注释的常见借口，并强调了注释在软件设计中的重要作用。

四个借口及其反驳：

1. **“好的代码是自解释的”**：这是一个谬误。代码无法表达所有的设计信息，如高层级的抽象、设计决策背后的考量等。没有注释，就没有抽象，因为用户必须阅读实现才能理解其行为。
2. **“我没有时间写注释”**：这是战术式编程的体现。写注释是一项投资，能提高软件的可维护性，很快就能收回成本。
3. **“注释很容易过时”**：这在实践中不是主要问题。将注释放置在代码附近，并通过代码审查可以有效地保持其更新。
4. **“我所看到的注释都是毫无价值的”**：这可能是最有道理的借口，但问题是出在注释的质量上，而不是注释本身。

好的注释能降低认知负荷，减少“未知的未知”，并阐明依赖关系和消除模糊性。

### 第 13 章 注释应该描述代码中难以理解的内容

本章给出了编写好注释的具体指导原则。核心思想是：**注释应该描述代码中自身难以表达清楚的内容**。

- **13.2 不要重复代码**
  - 最常见的坏注释就是重复代码。如果注释里的信息可以轻易地从代码本身推断出来，那么这个注释就没有价值。好的注释应该使用与被描述实体不同的词汇来提供额外信息。
- **13.3 更低层级的注释可提高精确度**
  - 这类注释通过阐明代码的确切含义来增加精确性，常用于变量声明。它们应该说明单位、边界条件（包含还是排除）、null 值的含义等。
- **13.4 更高层级的注释可增强直觉**
  - 这类注释比代码更抽象，它们忽略细节，帮助读者理解代码的整体意图和结构（“做什么”和“为什么这么做”）。例如，在一个循环前写下注释，描述这个循环的整体目标。
- **13.5 接口文档**
  - 接口注释是定义抽象的关键，应该完整地描述用户需要知道的一切，而无需阅读实现。它包括：方法的高层级行为描述、每个参数和返回值的精确说明、副作用、可能抛出的异常以及调用前必须满足的前提条件。
- **13.6 实现注释**
  - 方法内部的注释，用于解释代码在内部如何工作。它们应描述“做什么”和“为什么”，而不是“如何做”。

### 第 14 章 选取名称

本章强调了命名在软件设计中的重要性。好的名称是一种文档形式，能让代码更易懂，而坏的名称会造成歧义和缺陷。

- **14.1 示例：坏名称会导致代码缺陷**
  - 作者讲述了一个因变量名 `block` 被用于两种不同目的（逻辑块号和物理块号）而导致的、耗时六个月才找到的严重缺陷。
- **14.2 创造画面**
  - 命名的目标是在读者脑海中创造一幅关于被命名实体本质的清晰画面。一个好的名称是一种抽象，它突出了实体最重要的方面。
- **14.3 名称应该是精确的**
  - 名称最常见的问题是过于笼统或含糊，例如 `count` 或 `status`。如果很难为一个变量找到一个精确的名称，这通常是危险信号，表明该变量可能没有清晰的定义或目的。
- **14.4 命名要确保一致性**
  - 对于反复出现的同类事物，应该始终使用相同的名称。这能创造认知杠杆，让开发者可以重用已有的知识。

### 第 15 章 先写注释

本章提倡一种激进但有效的方法：在编写代码之前先写注释。

- **15.1 迟到的注释不是好注释**
  - 将写注释推迟到最后，通常意味着注释质量差或者根本就不会写。因为此时开发者已心不在焉，对设计的记忆也已模糊。
- **15.2 先写注释**
  - 作者的流程是：先写类接口注释，然后写重要公有方法的接口注释和签名（方法体为空），然后是实例变量和它们的注释，最后才填充方法体。
- **15.3 注释是一种设计工具**
  - 先写注释的最大好处是**它能改善设计**。注释是捕获和评估抽象的唯一方式。如果一个方法或变量需要很长很复杂的注释来描述，这本身就是一个危险信号，说明其设计可能不够简洁（即它不够“深”）。通过在编码前编写和简化注释，可以及早发现并修复设计问题。

### 第 16 章 修改现有的代码

本章讨论了在软件演进过程中如何维护简洁的设计。

- **16.1 保持战略式的思考**
  - 在修改现有代码时，必须抵制“做出最小改变”的战术式诱惑。理想情况下，完成每次变更后，系统的结构应该像是在设计之初就考虑到了这次变更一样。这意味着需要进行重构，持续地改善设计。如果你没有使设计变得更好，你很可能就在使它变得更糟。
- **维护注释**
  - **将注释放置在代码附近**：将接口注释放在方法实现的正上方，而不是头文件中，这样修改代码时更容易看到并更新它。
  - **注释属于代码，而不是提交日志**：重要的设计决策和变更原因应该记录在代码的注释中，而不是只放在版本控制的提交信息里，因为后者很难被未来的开发者发现。
  - **避免重复**：每个设计决策应只被精确地记录一次。如果信息已在外部文档（如协议规范）中记录，只需在代码中引用它，不要重复。

### 第 17 章 一致性

本章强调一致性是降低复杂性的一个强大工具。

- **17.1 一致性示例**
  - 一致性意味着相似的事情以相似的方式完成，而不同的事情则以不同的方式完成。它体现在**名称**、**编码风格**、**接口**和**设计模式**等多个方面。一致性能创造认知杠杆，让开发者可以快速地应用已有知识。
- **17.2 确保一致性**
  - **文档**：将重要的约定（如编码风格）记录下来。
  - **强制执行**：使用自动化工具检查并强制执行约定是最好的方法。
  - **入乡随俗**：在修改代码时，遵循现有代码的约定。
  - **不要轻易改变现有约定**：引入不一致的代价通常比新方法带来的微小改进要大得多。只有当新方法有压倒性优势，并且你愿意去更新所有旧用法时，才应该这样做。

### 第 18 章 代码应该是易理解的

本章讨论了如何编写易于理解（obvious）的代码来对抗模糊性。

如果代码是易理解的，人们可以快速阅读并正确地猜测其行为。

**使代码更易理解的事情**：

- **好的名称和一致性**：这是最重要的两点。
- **明智地使用空格**：用空行来分隔代码块，可以使结构更清晰。
- **注释**：当代码不可避免地变得复杂时，用注释来弥补缺失的信息。

**使代码难理解的事情**：

- **事件驱动编程**：控制流难以跟踪，需要在处理函数的注释中说明其被调用的时机。
- **通用容器**：像 Java 的 `Pair` 或 C++ 的 `std::pair` 会导致代码含义模糊，因为元素的名称（如 `key`, `value`）是通用的。最好定义专用的类或结构来代替它们。
- **软件应被设计成易于阅读的，而不是易于编写的**：这是贯穿本章的一条通用规则。

### 第 19 章 软件发展趋势

本章从复杂性的角度分析了几种流行的软件开发趋势。

- **19.1 面向对象编程和继承**
  - **接口继承**有助于降低复杂性，因为它通过一个通用接口服务于多种目的，使得接口更“深”。
  - **实现继承**则很危险，因为它在父类和子类之间创建了强依赖和信息泄露。应谨慎使用，并优先考虑组合。
- **19.2 敏捷开发**
  - 敏捷的增量式开发理念是好的，但它有鼓励**战术式编程**的风险，因为它倾向于关注功能而非抽象。作者认为，增量开发的单元应该是抽象，而不是功能。
- **19.3 单元测试**
  - 单元测试对于软件设计至关重要，因为一个好的测试套件能让开发者有信心进行重构，从而持续改进设计。
- **19.4 测试驱动开发 (TDD)**
  - 作者对 TDD 持批评态度，认为它将注意力集中在让特定功能通过测试，而不是寻找最佳设计，这是一种纯粹的战术式编程。
- **19.5/19.6 设计模式 / Getters 和 Setters**
  - 设计模式在适用时是好的，但有被过度使用的风险。Getter 和 Setter 就是一个例子，它们是浅方法，过度使用会暴露实现细节，违反信息隐藏原则。

### 第 20 章 性能设计

本章讨论了如何在不牺牲简洁设计的前提下实现高性能。

- **20.1 如何考虑性能**
  - 简单的代码通常比复杂的代码运行得更快。开发过程中，应了解哪些操作是根本上开销大的（如网络、磁盘I/O、内存分配），并在设计时自然地选择更高效的方案，前提是它不会增加复杂性。
- **20.2 修改前（和修改后）的测量**
  - 在进行任何性能优化之前，必须先测量，以找到真正的瓶颈，并为后续的改进提供基线。程序员对性能的直觉是不可靠的。
- **20.3 围绕关键路径进行设计**
  - 当需要优化时，关键思想是围绕**关键路径**（critical path）进行设计。首先设想出执行最常见情况所需的最少量代码（“理想的代码”），然后重构系统，使其尽可能接近这个理想状态，同时保持简洁的抽象。这通常意味着将所有特殊情况的检查从关键路径中移出。
- **20.4 示例：RAMCloud 缓冲区**
  - 作者通过重构 `Buffer` 类的例子，展示了如何通过简化关键路径（将多个方法调用和条件检查合并为一个）来同时提升性能和简化设计，最终代码量减少了20%，而性能提升了近两倍。

### 第 21 章 决定什么是重要的

本章总结了良好软件设计的核心能力：区分重要和不重要。

软件设计应该围绕重要的事情进行，并将其突出显示；而不重要的事情应该被隐藏和最小化。

- 如何决定什么是重要的？
  - 寻找**杠杆点**，即一个能解决许多问题的方案，或者一个能帮助理解许多其他事情的信息。例如，一个通用的接口比多个专用的方法更有杠杆作用。
- 最小化重要的事情
  - 如果可能，尽量减少重要事物的数量和它们出现的地方。
- 如何强调重要的事情
  - 通过**突出显示**（如在接口或名称中）、**重复**和**中心化**（使其成为系统结构的核心）来强调重要概念。
- 常见的错误
  - 一是认为重要的东西太多，导致浅的类和不必要的复杂性。二是未能认识到某些事情的重要性，导致信息被隐藏。

拥有区分重要与否的能力，作者称之为“好的品味”，是成为一名优秀软件设计师的关键。

### 第 22 章 结论

本章是全书的总结，重申了核心主题：**复杂性是软件设计中最重要的挑战**。

作者回顾了书中提出的核心思想，如创建更深和更通用的类、通过定义来规避错误等。这些方法都需要在项目早期投入额外的工作量，这是一种**投资思维**。

最后，作者指出，如果将良好的设计作为目标，编程本身会变得更加有趣，它就像一个“如何用最简单的结构解决特定问题”的迷人谜题。对设计的投资将很快获得回报，不仅能更快地生产出更高质量的软件，而且开发过程本身也会更加愉快，因为你会花更多时间在有趣的设计阶段，而不是在复杂代码中痛苦地调试。
